01

Foundation Concepts You Built Upon

Your entire project is built on three pillars. Understanding these deeply will win you any interview question on networking.

TCP (SOCK_STREAM) Connection-oriented. Guarantees delivery, ordering, and error-checking. You used this for WebSocket — correct, because WS requires reliability. The cost is latency from ACKs and congestion control.
UDP (SOCK_DGRAM) Connectionless. No delivery guarantee, no ordering, no handshake. Lower latency, higher packet loss. Used in gaming, live video, DNS. You did NOT use UDP — but understanding why helps justify TCP for WS.
TCP Flags SYN (initiate), SYN-ACK (server agrees), ACK (confirm), FIN (close gracefully), RST (hard reset). The 3-way handshake (SYN→SYN-ACK→ACK) is what happens before your WebSocket can even start.

socketcreation.c — ESP32 WiFi AP + TCP Echo Server

.C
main.c socketcreation.c/main/

What it does: ESP32 runs as a WiFi Access Point (AP) with SSID "Doraemon". Devices connect to it, then connect via TCP to 192.168.4.1:3333. Any message sent is echoed back.

WiFi AP Mode vs STA Mode:

AP Mode (Access Point) ESP32 creates its own WiFi network. Other devices join it. ESP32 gets IP 192.168.4.1 by default. Good for standalone scenarios — no router needed. Used in socketcreation.c.
STA Mode (Station) ESP32 joins an existing WiFi network like any other device. Gets IP from router DHCP. Used in ALL later projects — needed to be on the same network as your laptop.
✓ First ESP-IDF TCP socket — correct use of lwIP ✓ NVS flash init — required for WiFi credentials storage ✓ FreeRTOS task (xTaskCreate) — non-blocking app_main ✗ bind() return value not checked ✗ Only one client at a time in outer while loop ⚠ Hardcoded credentials — fine for dev, not for production

NVS (Non-Volatile Storage): ESP32 stores WiFi config and other data in flash memory using a key-value store. nvs_flash_init() must always be called before WiFi init — if flash is full or corrupted, erase and reinit.

websocket_handshake — The Core Achievement

This is where the real work happened. You implemented the entire WebSocket protocol from scratch. Let's break every part down.

.C
main.c websocket_handshake/main/

The WebSocket Handshake — Step by Step

1

Browser sends HTTP Upgrade Request

Contains: GET / HTTP/1.1, Upgrade: websocket, Connection: Upgrade, Sec-WebSocket-Key: [random base64 string]

2

ESP32 extracts the Sec-WebSocket-Key

Your strcasestr_custom() does case-insensitive search for "Sec-WebSocket-Key: " in the raw HTTP buffer. Then reads until \r\n.

3

Concatenate key + GUID

Append the magic string "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" (defined in RFC 6455) to the client's key.

4

SHA-1 hash the combined string

mbedtls_sha1() produces a 20-byte hash. This is the same library used for TLS — Espressif ships it with ESP-IDF.

5

Base64 encode the SHA-1 hash

mbedtls_base64_encode() converts the 20 binary bytes into ~28 printable characters — the Sec-WebSocket-Accept header value.

6

Send HTTP 101 Switching Protocols

After this response, the TCP connection is promoted to a WebSocket channel. All subsequent data uses WS frame format — not HTTP.

WebSocket Frame Parsing — What Your Code Does

// Read first 2 bytes of frame header uint8_t opcode = hdr[0] & 0x0F; // low 4 bits of byte 0 uint8_t mask = (hdr[1] >> 7) & 1; // bit 7 of byte 1 uint64_t plen = hdr[1] & 0x7F; // low 7 bits of byte 1 // If plen == 126: next 2 bytes are actual length // If plen == 127: next 8 bytes are actual length // Opcode 0x1 = text, 0x2 = binary // Opcode 0x8 = close, 0x9 = ping, 0xA = pong // Bit 7 of byte 0 = FIN bit (1 = complete frame)

Latency Optimisations in This File

TCP_NODELAY (Nagle's Algorithm Disabled)
TCP_NODELAY = 1
By default, TCP buffers small packets and waits to batch them (Nagle's algorithm). This adds up to 40ms of extra latency per message. Setting TCP_NODELAY forces immediate send. This is THE most important latency fix for your use case.
WIFI_PS_NONE (Power Saving Off)
WIFI_PS_NONE
By default, ESP32 WiFi sleeps between beacon intervals (~100ms) to save power. This adds random delays to every packet. Disabling power save keeps the radio always-on. Adds ~100mA power draw but cuts latency dramatically.
✓ TCP_NODELAY — kills Nagle latency ✓ WIFI_PS_NONE — kills WiFi sleep latency ✓ Per-client FreeRTOS task — true concurrency ✓ Ping/Pong opcode handling (0x9 / 0xA) ✓ Close frame handling (opcode 0x8) ✓ Dynamic malloc for payload — handles variable length ✗ malloc without free on error paths — memory leak ✗ recv() used multiple times — partial read possible under load ✗ No timeout on recv — client can hang the task forever ⚠ WiFi connect is async — socket server could start before IP is ready

websocket_handshake2 — select()-based Multi-client

.C
main.c websocket_handshake2/main/

What changed: Instead of spawning a FreeRTOS task per client, this version uses a single event loop with select() to monitor all client sockets simultaneously. Supports up to 5 clients (MAX_CLIENTS = 5).

select() vs FreeRTOS Tasks — The Fundamental Trade-off
AspectFreeRTOS Task per Clientselect() Event Loop
Multi-client handlingOne task per client, truly parallelSingle task, round-robin polling
Memory~4-8KB stack per clientSingle task stack, O(1)
LatencyBest — each client gets dedicated CPUSlightly higher — serialised
ScalabilityLimited by RAM (ESP32 has ~320KB)Limited only by open file descriptors
Blocking I/OOK — blocks only this taskMust use MSG_DONTWAIT or non-blocking
Code complexitySimple per-client codeMore complex state management

Key implementation details:

The clients[] array tracks active sockets. fd_set is a bitmask of file descriptors to watch. select(max_fd+1, &read_fds, NULL, NULL, &tv) — the first arg must be max_fd+1 (a common bug is forgetting the +1). The 5ms timeout (tv_usec = 5000) prevents busy-waiting.

Persistent payload_buf Unlike handshake1 which malloc'd per frame, handshake2 uses a global uint8_t payload_buf[MAX_PAYLOAD_LEN+1]. This avoids heap fragmentation on the ESP32 — critical for long-running embedded systems. The downside is it's not re-entrant (which is fine for a single-thread event loop).
✓ select() — no FreeRTOS task per client ✓ SO_REUSEADDR — proper port reuse ✓ TCP_NODELAY on every accepted socket ✓ Persistent buffer — no malloc in hot path ✓ MSG_DONTWAIT — non-blocking recv ✗ clients[].active never set to 0 on disconnect ✗ No broadcast to all clients (only echo back) ⚠ max_fd tracking is naive — could use a sorted structure

.CPP

Three classes in one file:

Recursive accept_client() — clever but risky Instead of a while(1) loop, WebSocketServer::accept_client() calls itself after spawning each client task. This avoids stack buildup in the main server loop but means each accepted client call is a new stack frame on the calling task. With many rapid connections, this could overflow the server task's stack. The while(1) version is safer.

Lambda task creation:

xTaskCreate([](void *param) { WebSocketClient client((int)(intptr_t)param); client.handle(); }, "handle_client", 8192, (void *)(intptr_t)sock, 5, NULL);

The lambda captures nothing (stateless), so it's compatible with the C-style function pointer FreeRTOS expects. Clever use of C++11 in an ESP-IDF context.

✓ Clean OOP — each class has single responsibility ✓ WIFI_PS_NONE — latency optimisation preserved ✓ TCP_NODELAY on every client socket ✗ Recursive accept — potential stack overflow under rapid connections ✗ All classes in one file — harder to maintain as it grows

bt_l2cap_server — Bluetooth Classic L2CAP Server

BT
main.c + bt_app_core.c/h bt_l2cap_server/main/

This is the most advanced and different module — exploring Bluetooth Classic as an alternative transport to WiFi+WebSocket. Key concepts:

L2CAP (Logical Link Control and Adaptation Protocol)

L2CAP sits directly above the Bluetooth baseband layer. It provides channel-based communication, fragmentation/reassembly, and QoS. It's like the "TCP" of Bluetooth — lower level than RFCOMM (which is the "serial port" abstraction), lower latency, higher throughput potential.

SDP (Service Discovery Protocol)

Before connecting, a Bluetooth client uses SDP to discover what services the server offers and which PSM (Protocol/Service Multiplexer — like a port number) to connect on. You registered a custom SDP record with a dynamic PSM 0x1001.

bt_app_core.c — The Message Queue Architecture

Why the message queue pattern? Bluetooth callbacks run in the Bluetooth controller context — not safe to call ESP-IDF WiFi/socket APIs from there. The solution: callbacks post a message to a FreeRTOS queue, and a separate "BtAppTask" dequeues and processes them in a safe context. This is the standard pattern for event-driven embedded BT development.
// bt_app_core.c: FreeRTOS queue-based dispatcher s_bt_app_task_queue = xQueueCreate(10, sizeof(bt_app_msg_t)); xTaskCreate(bt_app_task_handler, "BtAppTask", 3072, NULL, configMAX_PRIORITIES - 3, &s_bt_app_task_handle); // High priority (MAX-3) ensures BT events are processed quickly

Core Concepts — Deep Explanations

Nagle's Algorithm — The Star of Your Internship

What is Nagle's Algorithm? Invented by John Nagle in 1984. The rule: if there is unacknowledged data in flight, buffer new small packets until either (a) the buffer is full (MSS), or (b) the ACK arrives. This was designed for telnet over slow WANs where sending 1-byte packets for each keypress was wasteful. For your robotics use case — sending small sensor readings or commands — Nagle's algorithm adds up to 40ms of buffering delay before each send. Disabling it with TCP_NODELAY is the single most impactful latency fix.

lwIP — The TCP Stack Under Everything

lwIP (Lightweight IP) All your socket calls — socket(), bind(), send(), recv() — go through lwIP, not the Linux kernel. lwIP is a tiny open-source TCP/IP stack designed for embedded systems. Espressif integrated it into ESP-IDF. The #include "lwip/sockets.h" header provides a POSIX-compatible socket API on top of lwIP — which is why your 1stLab Linux code and your ESP32 code look so similar.

mbedTLS — Why SHA-1 + Base64 in ESP-IDF

mbedTLS on ESP32 Normally used for TLS/SSL. You used it for WebSocket handshake key generation because it's already available in ESP-IDF. mbedtls_sha1() and mbedtls_base64_encode() are well-tested, hardware-accelerated cryptographic functions. The ESP32 has a hardware SHA accelerator — so your SHA-1 computation is very fast even on a microcontroller.

Interview Q&A — Be Ready for These

Q: What is Nagle's algorithm and why did you disable it?
A: Nagle's algorithm buffers small TCP packets until either the buffer fills to MSS size or an ACK arrives for previous data. This reduces network overhead for chatty connections but adds up to 40ms latency per small message — unacceptable for real-time robot control. We set TCP_NODELAY = 1 on every accepted socket to force immediate transmission of each message.
Q: Explain the WebSocket handshake from scratch.
A: The browser sends an HTTP GET with "Upgrade: websocket" and a base64-encoded random 16-byte nonce as "Sec-WebSocket-Key". The server concatenates this key with the RFC 6455 magic GUID "258EAFA5-E914-47DA-95CA-C5AB0DC85B11", computes SHA-1, base64-encodes the result, and returns it as "Sec-WebSocket-Accept" in a "101 Switching Protocols" response. After this, both sides communicate using binary WebSocket frames — not HTTP.
Q: How does your server handle multiple clients?
A: Two approaches. In websocket_handshake, we spawn a FreeRTOS task (xTaskCreate) for each accepted client — true concurrency, ~8KB stack per client. In websocket_handshake2, we use a select()-based single-threaded event loop with MSG_DONTWAIT non-blocking reads — more memory-efficient but serialised. The final OOP version uses FreeRTOS tasks with heap-allocated handler objects that self-delete when the client disconnects.
Q: What is the difference between TCP and UDP and when would you use each?
A: TCP is connection-oriented, guarantees delivery, ordering, and error correction via retransmission and ACKs. UDP is connectionless, faster, no guarantees. For WebSocket we need TCP because the protocol requires reliable, ordered delivery. For a live video stream or gaming, UDP with application-layer error correction is better — latency matters more than perfect reliability.
Q: Why did you use WIFI_PS_NONE?
A: ESP32's default WiFi power saving mode puts the radio into periodic sleep between beacon intervals (~100ms). Incoming packets are buffered at the access point and delivered on wake. This adds non-deterministic latency of up to 100ms. For real-time bidirectional communication, we set WIFI_PS_NONE to keep the radio always-on. The trade-off is higher current draw (~100mA more), which is acceptable for a tethered robot application.
Q: What is L2CAP and how does it differ from using WiFi+TCP?
A: L2CAP (Logical Link Control and Adaptation Protocol) is a Bluetooth protocol layer that provides channel-based communication directly over Bluetooth baseband — no IP stack involved. It has lower stack overhead than WiFi+TCP+WebSocket and is better suited for short-range, peer-to-peer communication. However, it requires device pairing, has lower throughput than WiFi (typically ~1-3 Mbps vs 50+ Mbps), and shorter range (~10m vs 50m). We explored it as an alternative for use cases where WiFi infrastructure isn't available.
Q: What are TCP flags and how does a connection close?
A: TCP uses flags in its header — SYN (synchronise sequence numbers), ACK (acknowledge), FIN (finish), RST (reset), PSH (push data immediately). A connection closes with a 4-way handshake: client sends FIN, server ACKs, server sends FIN, client ACKs. A RST forcefully closes without negotiation. In our WebSocket code, we handle the WS close frame (opcode 0x8) gracefully before calling close() on the socket.
Q: Why does your OOP version use extern "C" for app_main?
A: C++ uses name mangling — it encodes function parameter types into the symbol name to support overloading. ESP-IDF looks for the symbol "app_main" by its exact C name. Without extern "C", the compiler would emit a mangled symbol like "_Z8app_mainv" which the linker can't find. extern "C" tells the compiler to use C linkage (no mangling) for that function.

Enhancements & GitHub Publishing Tips

Critical Bugs to Fix Before GitHub

1. Remove hardcoded passwords from all files "gargi04**2006", "doraemon04**2006", "gargi04**2006" — these appear in multiple files. Move to a Kconfig/menuconfig system or a gitignored secrets.h. Never push credentials to public repos.
2. Fix recv() partial reads TCP is a stream — a single recv() may not return the full expected bytes. For the 2-byte header: while(bytes_read < 2) bytes_read += recv(sock, hdr+bytes_read, 2-bytes_read, 0);
3. Add SO_RCVTIMEO timeout to all recv() calls Without a timeout, a client that connects but never sends can block a task forever. Set a 30-second receive timeout on every accepted socket.
